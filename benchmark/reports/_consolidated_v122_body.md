# Rune Latency — pyenvector 1.2.2 (rmp / flat) 통합 리포트

3개 기능(`recall` / `searchable` / `capture`)을 **인덱스 크기(N)를 단계별로
키워가며 측정**한 결과를 하나로 묶은 리포트다(이하 "크기별 측정"). 인덱스를
100건부터 100,000건까지 정해둔 8개 크기로 한 칸씩 키우며 같은 측정을 반복하는
방식인데, 벤치마크 코드·원본 파일명에서는 이 방식을 **"sweep"(쓸고 지나간다)**이라
부른다 — 아래에서 "크기별 측정"과 "sweep"은 같은 말이다. 각 기능은
따로 측정했고(이유는 §2), 여기서는 동일 SDK·동일 인덱스 설정 아래의 결과를
한자리에 모아 해석한다. **다음 단계는 v1.4.3(`mm32 / ivf_vct`)와의 비교**이며, 이
리포트는 그 비교에 그대로 끼워넣을 수 있는 형태로 정리했다(§5).

원본별 리포트:
`latency_sweep_v122_rmpflat_recall_2026-05-26.md`,
`latency_sweep_v122_rmpflat_searchable_2026-05-26.md`,
`latency_sweep_v122_rmpflat_capture_2026-05-26.md`.

이 리포트에서 **사전 적재**란 측정 전에 인덱스를 N개 레코드로 미리 채워 크기
조건(N)을 만드는 단계를 가리킨다(원문 코드의 `prime`).

**기능 제시 순서.** 순서는 recall → searchable → capture다. recall을 맨 앞에 둔
이유는, 읽기 전용이라 회차마다 인덱스가 변하지 않아 같은 조건이 정확히 반복되고
v1.4.3와 가장 곧바로 맞댈 수 있는 비교축이기 때문이다(이 평가의 1차 산출물).
searchable과 capture는 둘 다 회차마다 insert가 1건씩 누적돼(아래 신뢰도 항목)
깨끗함에 차이가 없으므로, 둘 사이 순서에 별도 기준은 없고 v1.4.3 통합 리포트와
나란히 읽도록 같은 순서를 따랐다.

- **신뢰도(validity):** *측정된* 값이 그 조건의 진짜 지연시간인가. 시나리오 간
  오염은 두 장치로 차단했다(§2) — 시나리오별 fresh index 격리 + 기능별 분리
  측정. 그래도 capture/searchable에는 한 가지가 남는다: 같은 (N, scenario) 안에서
  측정 회차마다 capture(=insert 1건)가 누적돼 인덱스가 N → N+(회차수)로 미세하게
  커진다. `recall`은 읽기 전용이라 이 회차 간 누적조차 없어, 같은 조건의 반복
  회차가 정확히 동일 조건이다.

v1.2.2는 이 grid(100~100,000)에서 **세 기능 모두 결측 없이 전 구간을 측정**했다 —
v1.4.3가 capture에서 친 insert ceiling("0 available")이 나타나지 않았다. 그 ceiling은
v1.4.3의 IVF_VCT 적재 경로(shard 단위 merge 상태를 보는
`remaining_insertable_vectors_guaranteed` 카운터)에서 나오는데, v1.2.2 flat 적재는
이 경로 자체를 타지 않는다(어댑터가 `call_insert`를 직접 호출). 따라서 "여유분이 더
많아서"가 아니라 **그 제약을 만드는 적재 경로가 flat에 없어서**에 가깝다(코드 근거는
§4.3).

## 1. 무엇을 보려는 측정인가

v1.2.2의 `rmp + flat`에서, 인덱스가 커질 때 지연시간이 어떻게 변하는가? 이것이
운영 인덱스의 **기준선(baseline)**이다.

`flat` 인덱스는 쿼리마다 인덱스의 **모든 벡터를 전수 탐색**한다. 그래서 훑는 벡터
수가 곧 N이고, 검색 비용(`score`)이 **N에 비례(선형, O(N))**해서 커질 것으로
예상된다. centroid를 골라 일부만 훑는 구조(`ivf_vct`)가 아니라 전부 훑으므로,
검색 비용이 평평해지는 전환점(crossover)이 **없다**.

| N | 훑는 벡터 수 | score 예상 거동 |
|---|---|---|
| 100 | 100 (전부) | 최소 |
| 1,000 | 1,000 (전부) | 약 10× |
| 10,000 | 10,000 (전부) | 약 100× |
| 20,000 | 20,000 (전부) | 약 200× |
| 25,000 | 25,000 (전부) | 약 250× |
| 32,000 | 32,000 (전부) | 약 320× |
| 50,000 | 50,000 (전부) | 약 500× |
| 100,000 | 100,000 (전부) | 약 1,000× |

> **(사실)** 위 표는 flat = 전수 탐색이라는 인덱스 구조에서 산술적으로 유도한
> 기대 거동이다. 실제 측정값이 이 O(N) 모델대로 움직이는지는 §4에서 데이터로
> 확인한다(상수항·오버헤드 때문에 비례 배수는 정확히 일치하지 않는다).

> **(전제)** `rmp / flat`은 **현재 운영(production) `runecontext` 인덱스**의
> 구성이다. 따라서 이 측정은 채택 전 평가가 아니라 운영 baseline의 특성 파악이며,
> v1.4.3(`mm32 / ivf_vct`, 아직 미적용) 평가의 비교 기준이 된다.

## 2. 측정 환경

세 기능은 **같은 날·같은 엔드포인트·같은 SDK·같은 인덱스 설정**으로 측정됐다.
v1.4.3와 달리 기능별로 측정일·클러스터가 갈리지 않는다.

| 항목 | recall / searchable / capture |
|---|---|
| 측정일 | 2026-05-26 |
| envector 엔드포인트 | `rune-bench-opo0wzsyy45s.clusters.envector.io` |
| sdk_version | 1.2.2 |
| eval_mode / index_type | rmp / flat |
| embedding_model | Qwen/Qwen3-Embedding-0.6B |
| embedding_mode | sbert |
| key_id | vault-key |
| vault_endpoint | tcp://193.122.124.173:50051 |
| insert_mode | single (읽기 전용 recall 제외) |
| 유효 회차 / warmup | 12 / 3 |
| 측정한 인덱스 크기(N) | 100 ~ 100,000 (8개 지점) |

**측정 격리 — 두 장치 (결정 2026-05-22).** `capture`/`searchable`은 측정 도중
insert가 일어나 인덱스 상태를 바꾼다. 이를 두 단계로 격리했다.

1. **시나리오별 격리.** mutating 시나리오(capture T1/T2/T3, searchable
   T10/T11/T12)는 (N, scenario)마다 **삭제+생성+사전 적재**를 새로 해 **빈
   인덱스에서 시작**한다. 시나리오 간 누적 오염을 차단한다.
2. **기능별 분리 측정.** recall/capture/searchable을 각각 따로 실행해, 한
   그룹의 insert가 다른 그룹의 row-insert 여유분을 잠식하지 못하게 했다.
   읽기 전용 recall은 (N, group)마다 한 번 drop+create+prime 해, 같은 N의
   T5/T6가 동일 인덱스를 공유한다.

이 두 격리로도 **막지 못하고 남는 것이 하나 있다**: 같은 (N, scenario)를 반복
측정하는 동안 회차마다 insert가 1건씩 쌓여, 인덱스가 N에서 N+15로 미세하게
커진다(warmup 3 + 유효 12회). 다만 v1.2.2 flat 적재는 v1.4.3가 ceiling을 만났던
IVF_VCT 적재 경로를 타지 않아(§4.3), 이 누적이 어느 N에서도 적재 거부로 번지지
않았다. `recall`은 insert가 없는 읽기 전용이라
이마저 없어, 측정된 N에서 회차마다 정확히 동일 조건이며, 이 평가의 **1차
산출물**이다.

> **(주의)** 각 단계 측정은 서버(클러스터) 쪽에서 계산되는 `score`를 제외하면
> 클라이언트 머신 영향을 받는다. v1.4.3 비교 시 두 SDK는 서로 다른 머신에서
> 돌지만, N에 따라 변하면서 가장 오래 걸리는 단계(`score`)는 서버 쪽 계산이므로
> 머신 차이는 주로 작은 단계들에만 영향을 준다.

## 3. 요약 결과

표 읽는 법: 행 = 사전 적재된 인덱스 크기 N, 열 = 각 단계의 p50(ms), 마지막 열만
total p95. 빈칸 = 해당 N 미측정. v1.2.2 rmp/flat은 이 grid에서 `ERROR`가 없다
(전 구간 측정 성공).

각 단계(표의 열)가 무엇을 재는지는 다음과 같다.

| 단계 | 등장 기능 | 의미 | 실행 위치 |
|---|---|---|---|
| `embed` | 공통 | 입력 텍스트·쿼리를 임베딩 벡터로 변환 | 로컬(Qwen 모델) |
| `score` | 공통 | 암호화된 벡터 유사도(내적)를 전수 계산 | 서버(envector) |
| `vault_topk` | 공통 | 상위 k개 후보를 Vault에서 복호화 | 원격 Vault(gRPC) |
| `remind` | recall | 복호화된 결과로 메타데이터(원문 등) 조회 | 로컬 |
| `insert` | capture | 암호화 후 인덱스에 1건 적재 | 서버 |
| `insert_searchable` | searchable | 적재 후 검색 가능(SEARCHABLE) 상태가 될 때까지 폴링 대기 | 클라이언트 폴링 + 서버 |
| `total` | 공통 | 입력부터 끝까지 전체 소요(end-to-end) | — |

기능별 단계 순서:
- **recall**: embed → score → vault_topk → remind → total
- **searchable**: embed → score → vault_topk → insert_searchable → total
- **capture**: embed → score → vault_topk → insert → total

> **(searchable 단계 주의)** v1.2.2의 searchable은 적재 후 검색 가능까지를
> `insert_searchable` **한 단계(폴링)**로 잰다. v1.4.3는 같은 구간을 `insert_rpc`
> → `merge_wait` → `publish_wait` **세 단계(서버 push)**로 나눠 잰다. 측정
> 메커니즘이 다르므로 비교에서는 단계 분해를 맞대지 않고 total만 본다(§5).

측정에 쓰인 시나리오는 다음과 같다.

| 시나리오 | 기능 | 입력 | 측정 의도 |
|---|---|---|---|
| `T1_short_en` | capture | 짧은 영어 (약 30 토큰) | 짧은 텍스트 적재 |
| `T2_long_en` | capture | 긴 영어 (약 150 토큰) | 긴 텍스트 적재 |
| `T3_korean` | capture | 한국어 | 한국어 적재(토큰화 특성 반영) |
| `T5_exact_match` | recall | 인덱스에 있는 항목과 같은 텍스트로 검색 | 정확 일치 검색 |
| `T6_cross_lang` | recall | 한국어 쿼리로 영어 문서 검색 | 교차언어 검색 |
| `T10_short_en_searchable` | searchable | T1과 같은 입력 | 적재 → 검색 가능(SEARCHABLE)까지 |
| `T11_long_en_searchable` | searchable | T2와 같은 입력 | 〃 |
| `T12_korean_searchable` | searchable | T3와 같은 입력 | 〃 |

searchable의 T10/T11/T12는 capture의 T1/T2/T3 입력을 그대로 재사용한다. 시나리오
번호가 비연속인 것은 원래 시나리오 체계에서 이 크기별 측정에 해당하는 것만 골랐기
때문이다(예: T4 중복 입력, T7 topk 변형, T8 vault_status는 이 측정에서 제외).

## 4. 해석

### 4.1 recall — flat 쿼리 비용이 N에 거의 선형으로 커진다 (핵심 관찰)

읽기 전용이라 데이터가 가장 깨끗하다. 가장 오래 걸리는 단계인 `score` p50를 N축으로 보면:

| N | 100 | 1,000 | 10,000 | 20,000 | 25,000 | 32,000 | 50,000 | 100,000 |
|---|---|---|---|---|---|---|---|---|
| T5 score p50 | 36.6 | 46.6 | 116.6 | 204.5 | 241.5 | 356.9 | 550.1 | 1087.3 |
| T6 score p50 | 36.8 | 47.2 | 114.6 | 202.9 | 234.6 | 353.2 | 560.1 | 1109.0 |

> **(사실)** N이 100에서 100,000으로 **1,000배** 커지는 동안 `score` p50는 약
> 37 ms에서 약 1,090 ms로 **약 30배** 커진다. N이 커질수록 score가 꾸준히 함께
> 커지며, 작은 N 구간(100→1,000)은 고정 오버헤드에 묻혀 거의 평평하다가 N이
> 1만을 넘어서면서 거의 비례에 가깝게 증가한다.

> **(추론)** 이는 §1의 flat 모델 — 쿼리가 전체 N개 벡터를 다 훑는다 — 과 부합한다.
> N이 커질수록 score가 함께 커지고, 평평해지는 구간이 없다.
>
> 다만 N은 1,000배 커졌는데 score는 30배만 커졌다. 이는 score를 직선으로 보면
> `score ≈ (벡터 1개당 비용)×N + (N과 무관한 고정 비용)` 두 항의 합이기 때문으로
> 읽힌다. 여기서 **고정 비용(상수항)**이란 인덱스에 벡터가 몇 개든 매 쿼리에 똑같이
> 드는 몫이다. 데이터로 보이는 근거는, N을 100→1,000으로 10배 늘려도 score가
> 36.6→46.6 ms로 약 10 ms밖에 안 는다는 점이다 — 작은 N의 score(~37 ms) 대부분은
> 벡터를 훑는 비용이 아니라 이 고정 비용이고, 벡터를 훑는 비용은 N이 1만을 넘어서야
> 눈에 띄게 지배한다. (이 고정 비용이 구체적으로 무엇인지 — 쿼리 암호화·전송 setup
> 등 — 는 이 측정만으로는 가를 수 없다.)

> **(한계)** "정확히 선형"이라고 단정하려면 더 촘촘한 N과 회차가 필요하다. 이
> 측정이 받쳐주는 진술은 "score가 N과 함께 단조 증가하며, 평평해지는 전환점이
> 보이지 않는다"까지다. flat이 큰 N에서 어디서 v1.4.3 ivf와 교차하는지는 v1.4.3
> 곡선을 겹쳐야 확정된다(§5).

단계별 합이 total과 맞는지도 확인된다(예: T5 N=100 → 63.9+36.6+8.4+15.5 ≈ 124.4
≈ total 126.5). 측정 자체의 내적 일관성은 양호하다.

### 4.2 searchable — 비용이 N에 따라 커지며, insert_searchable이 지배한다

`searchable`의 total(~0.4~2.7초)에서 `insert_searchable`(적재 후 검색 가능까지의
폴링 대기)이 가장 큰 몫이고, `score`가 그 다음이다. 둘 다 N에 따라 커진다.

> **(사실)** total은 N=100의 약 0.42초에서 N=100,000의 약 2.71초로 커진다(T10
> 기준). `insert_searchable`은 241 → 1,433 ms, `score`는 74 → 1,133 ms로 둘 다
> N에 따라 증가한다. 작은 N에서는 `insert_searchable`이, 큰 N에서는
> `insert_searchable`과 `score`가 비슷한 크기로 total을 양분한다.

> **(함의)** v1.2.2 searchable의 사용자 체감 지연은 N에 따라 수백 ms~수초 범위로
> 움직인다. 단, 이 값은 `insert_searchable` **단일 폴링 단계**로 측정된 것이라,
> 세 단계(서버 push)로 측정한 v1.4.3와는 단계 분해를 직접 맞댈 수 없고 비교에서는
> end-to-end total만 본다(§5).

### 4.3 capture — insert는 N에 무관하고, total 증가는 score가 끈다

`capture`의 total은 작은 N에서는 `insert`(~130~175 ms)가 가장 크지만, N이 커지면
`score`가 이를 추월해 total을 끈다. embed는 한국어(T3, ~120 ms)가 영어(T1,
~72 ms)보다 크다 — 토큰 수 차이로 자연스럽다.

> **(사실)** `insert` p50는 N=100의 ~146 ms에서 N=100,000의 ~170 ms로, N이
> 1,000배 커지는 동안 거의 변하지 않는다(1건 적재 비용은 인덱스 크기에 둔감하다).
> 반면 `score`는 같은 구간에서 ~66 → ~1,143 ms로 커진다. 그래서 capture total의
> N 의존성은 거의 전적으로 `score`에서 온다.

> **(사실)** v1.2.2 flat은 이 grid 전 구간(100~100,000)에서 capture가 ERROR 없이
> 측정됐다. §2의 회차 간 insert 누적이 있어도 적재가 거부되지 않았다. 즉 고-N
> capture 지연시간 경향을 이 측정으로 결론 낼 수 있다(v1.4.3가 N≥20,000에서 결측인
> 것과 대비된다).

> **(추론, 코드 근거)** v1.4.3가 친 ceiling("0 available")은 IVF_VCT 적재 경로의
> 서버측 카운터(`remaining_insertable_vectors_guaranteed`, shard 단위 merge 상태에
> 좌우됨 — `insertable_probe.py`)에서 나온다. v1.2.2 어댑터의 적재는 이 경로를 타지
> 않고 `call_insert`를 직접 호출하며, single-row insert·async merge·index load 같은
> 1.4.x 전용 단계가 없다(`runners/sdk/v122.py`: "v1.2.2 has no such paths"). 따라서
> v1.2.2가 이 grid에서 안 걸린 것은 "여유분이 더 많아서"라기보다 **그 제약을 만드는
> 적재 경로가 flat에 없어서**로 보는 게 코드에 부합한다.
>
> **(한계)** 단, 이 말이 "flat은 아무리 많이 넣어도 안 막힌다"는 뜻은 아니다. 우리가
> 측정한 범위는 N≤100,000까지이고, 그보다 더 큰 N에서, 또는 우리가 이번에 보지 않은
> 다른 서버측 용량 한계에서 막힐 가능성까지 이 측정으로 배제할 수는 없다. 확인된 것은
> "v1.4.3가 친 그 특정 ceiling은 flat 적재 경로에 없다"까지다.

### 4.4 꼬리 분포 — 두드러진 단발성 지연 없음

**먼저 "꼬리"가 뭔지.** 같은 (scenario, N)을 12회 반복 측정하면, 대부분의 회차는
비슷한 값(가운데값 = p50) 근처에 모이지만 가끔 한두 회차가 훨씬 느리게 나온다 —
네트워크 끊김·재접속, 일시적 서버 부하 같은 단발 사건 때문이다. 이렇게 드물게
튀는 느린 회차들이 분포의 **"꼬리(tail)"**이고, p95(상위 5% 지점)·p99가 이 꼬리를
잡아낸다. **p95가 p50과 가깝다 = 꼬리가 짧다(거의 모든 회차가 비슷)**, **p95가
p50보다 훨씬 크다 = 꼬리가 길다(가끔 크게 튄 회차가 있다)**는 뜻이다.

이 기준으로 보면, 전 (scenario, N)에서 total p95가 p50과 가깝게 붙어 있다(대체로
p50의 1.05~1.25배 범위). v1.4.3에서 보였던 수 분(分) 단위로 튄 회차(transport
재접속 등) 같은 긴 꼬리는 이 크기별 측정에 나타나지 않았다.

> **(사실)** 가장 벌어진 축에 속하는 T11 N=1,000도 p50 428.5 / p95 637.8(약
> 1.49배) 수준이고, 그 외에는 대부분 1.2배 이내다. p95를 성능 대표값으로 읽어도
> p50과 같은 결론(N에 따른 단조 증가)을 준다.

> **(함의)** 따라서 v1.2.2 크기별 측정은 비교에서 별도의 꼬리 각주나 제외 구간이
> 필요 없다 — 모든 grid point가 곡선 fit·비교에 그대로 쓰인다(§5).

## 5. v1.4.3 비교를 위한 준비

이 리포트는 v1.4.3(`mm32 / ivf_vct`) 곡선을 겹치기 위한 baseline이다. 비교
단계에서 반드시 지킬 것:

1. **양쪽의 측정 구간.** flat은 전수 탐색이라 검색 비용이 N에 비례하지만, 이
   측정에서는 외삽 없이 전 grid(100~100,000, 8개 지점)를 **직접 측정**했다(고-N도
   결측 없음). v1.4.3 ivf는 전환점에서 거동이 바뀌어 전환점(≈24,576)을 감싸도록
   직접 측정했다(20k/25k/32k). 비교는 두 곡선을 지연시간-vs-N 평면에 겹쳐 읽는다.
2. **`score`만 서버 쪽 계산.** 두 SDK는 서로 다른 머신에서 측정되지만, N에 따라
   변하면서 가장 오래 걸리는 단계(`score`)는 서버(클러스터) 쪽에서 계산되므로 머신
   차이의 영향이 작다. embed 등 작은 단계는 머신 차이를 탈 수 있으니 비교 본문에
   명시할 것. (특히 `score` 계산 클러스터의 하드웨어 사양이 두 버전에서 다를 수
   있으니, 비교 본문에서 이를 별도로 다룰 것.)
3. **단일 요인 해석 금지.** v1.2.2→v1.4.3은 eval_mode(rmp→mm32),
   index_type(flat→ivf_vct), 인프라가 **동시에** 바뀌었다. 지연시간 차이를 어느
   한 요인 탓으로 단정하지 말 것.
4. **searchable은 total만.** v1.2.2는 `insert_searchable` 단일 폴링, v1.4.3는
   `insert_rpc`+`merge_wait`+`publish_wait` 세 단계로 측정 메커니즘이 다르므로,
   단계별 분해 비교는 무의미하고 end-to-end total만 맞댄다.
5. **baseline 기준.** 이 5/26 크기별 측정이 v1.2.2 쪽 비교 데이터다. 과거 단발
   측정(`reports/past/`의 5/12·5/15)은 인프라·조건이 달라 이 비교에 섞지 않는다.
   (단발 SDK 비교에서 v1.2.2 baseline이 필요할 때는 5/15 aligned 측정값을 쓴다 —
   5/12 production-accumulated 아님.)
6. **제외할 구간 없음.** v1.2.2 크기별 측정은 ERROR 결측도, §4.4의 긴 꼬리도 없어,
   전 grid가 곡선 fit·비교에 그대로 쓰인다(v1.4.3가 capture 고-N 결측·꼬리 p95를
   제외·각주 처리해야 하는 것과 대비된다).
