# Rune Latency — pyenvector 1.4.3 (mm32 / ivf_vct) 통합 리포트

3개 기능(`recall` / `searchable` / `capture`)을 **인덱스 크기(N)를 단계별로
키워가며 측정**한 결과를 하나로 묶은 리포트다(이하 "크기별 측정"). 각 기능은
따로 측정했고(이유는 §2), 여기서는 동일 SDK·동일 인덱스 설정 아래의 결과를
한자리에 모아 해석한다. **다음 단계는 v1.2.2(`rmp / flat`)와의 비교**이며, 이
리포트는 그 비교에 그대로 끼워넣을 수 있는 형태로 정리했다(§5).

원본별 리포트:
`latency_sweep_v143_mm32ivf_recall_2026-05-26.md`,
`latency_sweep_v143_mm32ivf_searchable_2026-05-28.md`,
`latency_sweep_v143_mm32ivf_capture_2026-05-28.md`.

이 리포트에서 **사전 적재**란 측정 전에 인덱스를 N개 레코드로 미리 채워 크기
조건(N)을 만드는 단계를 가리킨다(원문 코드의 `prime`).

**기능 제시 순서와 그 근거 (두 축을 구분).** 순서는 recall → searchable →
capture이며, 기준은 "N=100k 실패 여부"가 **아니다** — 아래 두 축은 다른 개념이다.

- **결측(measurement gap):** 어떤 N을 아예 측정하지 못했는가. **N=100,000은 세
  기능 모두** 사전 적재 단계에서 동일하게 실패했다(`Index is not insertable … 0
  available`). 즉 100k 결측은 공통이며, 그 자리에 값이 *없다*는 뜻이지 있는 값을
  *못 믿는다*는 뜻이 아니다.
- **신뢰도(validity):** *측정된* 값이 그 조건의 진짜 지연시간인가. 시나리오 간
  오염은 두 장치로 차단했다(§2) — 시나리오별 fresh index 격리 + 기능별 분리
  측정. 그래도 capture/searchable에는 한 가지가 남는다: 같은 (N, scenario) 안에서
  측정 회차마다 capture(=insert 1건)가 누적돼 인덱스가 N → N+(회차수)로 미세하게
  커진다. `recall`은 읽기 전용이라 이 회차 간 누적조차 없어, 같은 조건의 반복
  회차가 정확히 동일 조건이다.

정렬 근거는 **(1) 측정 회차 간 인덱스 변화 유무 + (2) 유효 측정 N의 범위**다:
recall(읽기 전용, 100~50k 회차마다 동일 조건) → searchable(회차마다 insert 누적,
단 100k만 결측) → capture(insert ceiling이 N=20k부터 일찍 터져 유효 측정 N 자체가
적음). capture가 마지막인 것도 "100k 실패" 때문이 아니라 **유효 측정 N이 좁기**
때문이다.

## 1. 무엇을 보려는 측정인가

v1.4.3의 `mm32 + ivf_vct`가, 인덱스가 충분히 커진 영역에서 지연시간 이점을 내는가?

`ivf_vct` 인덱스는 약 4,096개 row마다 가상 centroid를 하나씩 만들고, 쿼리는 그중
`default_nprobe`개만 골라 훑는다. 그래서 centroid 수가 `nprobe`보다 적으면 쿼리가
**전부 훑어** flat scan과 같고, `nprobe`를 넘어서면 **일부(nprobe개)만 훑어**
인덱스가 더 커져도 쿼리 비용이 거의 늘지 않는다. 이번 설정은 `nprobe = 6`이므로
그 전환점(crossover)은 대략 `6 × 4096 ≈ 24,576`이다.

| N | centroid 수 ≈ ⌈N/4096⌉ | 쿼리가 훑는 centroid | 영역 |
|---|---|---|---|
| 100 | 1 | 1개 (전부) | flat과 동일 |
| 1,000 | 1 | 1개 (전부) | flat과 동일 |
| 10,000 | 3 | 3개 (전부) | flat에 가까움 (전환점 전) |
| 20,000 | 5 | 5개 (전부) | flat에 가까움 (전환점 바로 아래) |
| 25,000 | 7 | 6개 (7개 중) | 일부만 탐색 시작 (전환점 막 지남) |
| 32,000 | 8 | 6개 (8개 중) | 일부만 탐색 — 비용 거의 상수 |
| 50,000 | 13 | 6개 (13개 중) | 일부만 탐색 — 비용 거의 상수 |
| 100,000 | 25 | 6개 (25개 중) | 일부만 탐색 (단, 세 기능 모두 사전 적재 실패로 결측) |

> **(사실)** 위 표는 인덱스 파라미터(`nlist=8192`, `default_nprobe=6`)에서
> 산술적으로 유도된 것이다. 측정값이 이 모델대로 움직이는지는 §4에서 데이터로
> 확인한다.

> **(전제)** `ivf_vct`는 아직 운영(production)에 들어가지 않았다. 현재 운영
> `runecontext` 인덱스는 v1.2.2 `rmp/flat`이다. 이 측정은 채택 전 평가이며, 위
> 인덱스 파라미터는 운영 인덱스를 반영한 값이 아니라 평가용 선택값이다.

## 2. 측정 환경

세 기능은 **같은 SDK·같은 인덱스 설정**으로 측정됐다. 단, `recall`은 다른 날짜·
다른 클러스터 엔드포인트에서 돌았다(아래 표에서 구분).

| 항목 | recall | searchable / capture |
|---|---|---|
| 측정일 | 2026-05-26 | 2026-05-28 |
| envector 엔드포인트 | `runebench-0520-2-scfomauvy6cn` | `runebench-052701-czpcmtt1q9f3` |
| sdk_version | 1.4.3 | 1.4.3 |
| eval_mode / index_type | mm32 / ivf_vct | mm32 / ivf_vct |
| nlist / default_nprobe | 8192 / 6 | 8192 / 6 |
| embedding_model | Qwen/Qwen3-Embedding-0.6B | Qwen/Qwen3-Embedding-0.6B |
| embedding_mode | sbert | sbert |
| vault_endpoint | tcp://161.118.149.143:50051 | tcp://161.118.149.143:50051 |
| insert_mode | — (읽기 전용) | single |
| 유효 회차 / warmup | 12 / 3 | 12 / 3 |
| 측정한 인덱스 크기(N) | 100 ~ 100,000 (8개 지점) | 100 ~ 100,000 (8개 지점) |

`recall`은 별도 날짜·다른 엔드포인트에서 측정됐고, 그 외 SDK·인덱스·임베딩·Vault
설정은 searchable/capture와 동일하다.

**측정 격리 — 두 장치 (결정 2026-05-22).** `capture`/`searchable`은 측정 도중
insert가 일어나 인덱스 상태를 바꾼다. 이를 두 단계로 격리했다.

1. **시나리오별 격리.** mutating 시나리오(capture T1/T2/T3, searchable
   T10/T11/T12)는 (N, scenario)마다 **삭제+생성+사전 적재**를 새로 해 **빈
   인덱스에서 시작**한다. 시나리오 간 누적 오염을 차단한다.
2. **기능별 분리 측정.** recall/capture/searchable을 각각 따로 실행해, 한
   그룹의 insert가 다른 그룹의 row-insert 여유분
   (`remaining_insertable_vectors`)을 잠식하지 못하게 했다.

이 두 격리로도 **막지 못하고 남는 것이 하나 있다**: 같은 (N, scenario)를 반복
측정하는 동안 회차마다 insert가 1건씩 쌓여, 인덱스가 N에서 N+15로 미세하게
커진다(warmup 3 + 유효 12회). 같은 N을 잰다고 해도 회차마다 인덱스 크기가 조금씩
다른 셈이다. `recall`은 insert가 없는 읽기 전용이라 이마저 없어, 측정된 N에서
회차마다 정확히 동일 조건이며, 이 평가의 **1차 산출물**이다.

> **(주의)** 각 단계 측정은 서버(클러스터) 쪽에서 계산되는 `score`를 제외하면
> 클라이언트 머신 영향을 받는다. v1.2.2 비교 시 두 SDK는 서로 다른 머신에서
> 돌지만, N에 따라 변하면서 가장 오래 걸리는 단계(`score`)는 서버 쪽 계산이므로
> 머신 차이는 주로 작은 단계들에만 영향을 준다.

## 3. 요약 결과

표 읽는 법: 행 = 사전 적재된 인덱스 크기 N, 열 = 각 단계의 p50(ms), 마지막 열만
total p95. `ERROR` = 그 N에서 측정 실패(insert ceiling 또는 사전 적재 실패).
빈칸 = 해당 N 미측정. total p95에 붙은 `*(꼬리)*`는 그 값이 분포 꼬리에 섞인
단발성 지연이라 성능 대표값이 아니라는 표시다(자세히는 §4.4).

각 단계(표의 열)가 무엇을 재는지는 다음과 같다.

| 단계 | 등장 기능 | 의미 | 실행 위치 |
|---|---|---|---|
| `embed` | 공통 | 입력 텍스트·쿼리를 임베딩 벡터로 변환 | 로컬(Qwen 모델) |
| `score` | 공통 | 암호화된 벡터 유사도(내적) 계산 | 서버(envector) |
| `vault_topk` | 공통 | 상위 k개 후보를 Vault에서 복호화 | 원격 Vault(gRPC) |
| `remind` | recall | 복호화된 결과로 메타데이터(원문 등) 조회 | 로컬 |
| `insert` | capture | 암호화 후 인덱스에 1건 적재 | 서버 |
| `insert_rpc` | searchable | insert 요청 제출(서버가 병합을 비동기로 시작) | 클라이언트→서버 |
| `merge_wait` | searchable | 적재분이 병합 완료(MERGED_SAVED) 상태가 될 때까지 대기 | 서버 |
| `publish_wait` | searchable | load 후 검색 가능(SEARCHABLE) 상태가 될 때까지 대기 | 서버 |
| `total` | 공통 | 입력부터 끝까지 전체 소요(end-to-end) | — |

기능별 단계 순서:
- **recall**: embed → score → vault_topk → remind → total
- **searchable**: embed → score → vault_topk → insert_rpc → merge_wait → publish_wait → total
- **capture**: embed → score → vault_topk → insert → total

측정에 쓰인 시나리오는 다음과 같다.

| 시나리오 | 기능 | 입력 | 측정 의도 |
|---|---|---|---|
| `T1_short_en` | capture | 짧은 영어 (약 30 토큰) | 짧은 텍스트 적재 |
| `T2_long_en` | capture | 긴 영어 (약 150 토큰) | 긴 텍스트 적재 |
| `T3_korean` | capture | 한국어 | 한국어 적재(토큰화 특성 반영) |
| `T5_exact_match` | recall | 인덱스에 있는 항목과 같은 텍스트로 검색 | 정확 일치 검색 |
| `T6_cross_lang` | recall | 한국어 쿼리로 영어 문서 검색 | 교차언어 검색 |
| `T10_short_en_searchable` | searchable | T1과 같은 입력 | 적재 → 검색 가능(SEARCHABLE)까지 |
| `T11_long_en_searchable` | searchable | T2와 같은 입력 | 〃 |
| `T12_korean_searchable` | searchable | T3와 같은 입력 | 〃 |

searchable의 T10/T11/T12는 capture의 T1/T2/T3 입력을 그대로 재사용한다. 시나리오
번호가 비연속인 것은 원래 시나리오 체계에서 이 크기별 측정에 해당하는 것만 골랐기
때문이다(예: T4 중복 입력, T7 topk 변형, T8 vault_status는 이 측정에서 제외).

## 4. 해석

### 4.1 recall — ivf 쿼리 비용이 N에 거의 무관하다 (핵심 관찰)

읽기 전용이라 데이터가 가장 깨끗하다. 가장 오래 걸리는 단계인 `score` p50를 N축으로 보면:

| N | 100 | 1,000 | 10,000 | 20,000 | 25,000 | 32,000 | 50,000 |
|---|---|---|---|---|---|---|---|
| T5 score p50 | 898.8 | 934.5 | 999.0 | 1091.6 | 1059.8 | 1103.5 | 1078.9 |
| T6 score p50 | 796.9 | 805.1 | 1088.1 | 1020.1 | 957.2 | 1092.9 | 949.6 |

> **(사실)** N이 100에서 50,000으로 **500배** 커지는 동안 `score` p50는 대략
> **800~1,100 ms의 좁은 범위**에 머문다. N이 커질수록 꾸준히 커지는 양상은
> 보이지 않는다.

> **(추론)** 이는 §1의 ivf 모델 — 쿼리 비용이 `nprobe × 4096`개 벡터 수준에서
> 멈춘다 — 과 모순되지 않는다. 즉 인덱스가 커져도 검색 비용이 함께 커지지 않는
> 정황이 보인다.

> **(한계)** 다만 전환점(≈24,576) **바로 아래(20k)와 위(25k/32k/50k)의 단차**를
> 데이터에서 깔끔하게 분리해내긴 어렵다 — 회차 간 분산이 그 차이만큼 크다(부록의
> min/max 폭 참고). "전환점 위에서 비용이 상수가 된다"를 이 측정만으로 **단정할
> 수는 없고**, "N 전 구간에서 score가 폭증하지 않는다"까지가 데이터가 받쳐주는
> 진술이다. flat(N에 비례해 늘어나는 방식) 대비 실제 우위와 전환점 위치는
> v1.2.2 곡선을 겹쳐야 확정된다(§5).

단계별 합이 total과 맞는지도 확인된다(예: T5 N=100 → 52.7+898.8+8.5+76.2 ≈ 1036.2
≈ total 1035.8). 측정 자체의 내적 일관성은 양호하다.

### 4.2 searchable — 비용의 대부분은 서버측 병합 대기다

`searchable`의 total(~18.4~19.4초)에서 `merge_wait`이 ~15.6~15.9초로 **약 80%
이상**을 차지한다. 나머지는 `insert_rpc`(~1.3~1.6초), `score`(~0.8~1.0초),
`publish_wait`(0.2~0.5초) 순이다.

> **(사실)** `merge_wait`은 N=100부터 50,000까지 거의 일정하다(~15.6초 근처).
> insert한 레코드가 검색 가능(MERGED_SAVED) 상태가 될 때까지의 **서버측 병합
> 대기**이며, 인덱스 크기보다 서버 merge 파이프라인 특성에 좌우된다.

> **(함의)** searchable의 사용자 체감 지연(insert→검색가능 ~18초)은 클라이언트
> SDK나 eval_mode가 아니라 서버 merge가 좌우한다. v1.2.2 비교에서 searchable은
> SDK별 측정 메커니즘이 달라 단계별 분해를 직접 맞댈 수 없고 **total만** 비교
> 대상이다(§5).

### 4.3 capture — insert가 가장 오래 걸리는 단계이며, 고-N은 이 측정으로 결론 못 냄

`capture`의 total은 `insert`(~1,440~1,660 ms)와 `score`(~810~1,030 ms)가 양분한다.
embed는 한국어(T3, ~130 ms)가 영어(T1, ~75 ms)보다 크다 — 토큰 수 차이로 자연스럽다.

> **(사실)** N ≥ 20,000부터 ERROR가 불규칙하게 나타난다(T1은 25,000에서만 측정
> 성공, T2·T3은 20,000 이상 전부 실패). 원인은 SDK 지연시간이 아니라, 같은
> (N, scenario)에서 측정 회차마다 누적된 insert가 사전 적재로 채운 인덱스의
> row-insert 여유분(`remaining_insertable_vectors`)을 마저 소진해 "0 available"로
> 거부되는 것이다.

> **(함의)** 따라서 capture의 고-N 지연시간 경향은 이 측정으로는 결론 낼 수 없다.
> 단, 이는 *측정 결측*이지 측정된 값(N ≤ 10k, 그리고 T1의 25k)의 신뢰도 문제가
> 아니다.

### 4.4 꼬리 분포 — 인프라 변동이지 처리량 특성이 아님

두 지점에서 p95가 p50과 크게 벌어진다. 둘 다 분포의 꼬리에 섞인 단발성
이벤트로, SDK 처리량 특성으로 읽으면 안 된다.

- **recall T6 / N=10,000, total p95 ≈ 434,585 ms(약 7.2분).** 실행 로그(stderr)
  상 이 N 구간에서 gRPC 연결 끊김→재접속이 있었고(07:46~08:09 공백), 한 회차가
  그 재접속 창에 걸린 것으로 보인다. 같은 지점 p50은 1,253 ms로 정상이다.
- **searchable T12 / N=25,000·32,000, total p95 ≈ 33초** (p50 ~19초 대비). 역시
  꼬리에 섞인 지연이며 p50은 다른 N과 같은 수준이다.

> **(권고)** 비교·발표 시 이 두 p95는 각주로 "transport 재접속/꼬리 이벤트"임을
> 명시할 것. 그래야 이 숫자를 recall/searchable의 성능으로 오독하지 않는다.

## 5. v1.2.2 비교를 위한 준비

이 리포트는 v1.2.2(`rmp / flat`) 곡선을 겹치기 위한 토대다. 비교 단계에서 반드시
지킬 것:

1. **양쪽의 측정 구간을 다르게 잡는다.** flat은 전수 탐색이라 검색 비용이 N에
   정비례하고, 고-N은 측정에 시간이 너무 걸린다. 그래서 직접 잴 수 있는 작은
   구간만 재고 그 위는 직선으로 외삽한다(선형이라 외삽이 타당). v1.4.3 ivf는
   전환점에서 거동이 바뀌어 외삽이 안 되므로, 전환점(≈24,576)을 감싸도록 직접
   측정한다(20k/25k/32k 완료). 비교는 두 곡선을 지연시간-vs-N 평면에 겹쳐 읽는다.
2. **`score`만 서버 쪽 계산.** 두 SDK는 서로 다른 머신에서 측정되지만, N에 따라
   변하면서 가장 오래 걸리는 단계(`score`)는 서버(클러스터) 쪽에서 계산되므로 머신
   차이의 영향이 작다. embed 등 작은 단계는 머신 차이를 탈 수 있으니 비교 본문에
   명시할 것.
3. **단일 요인 해석 금지.** v1.2.2→v1.4.3은 eval_mode(rmp→mm32),
   index_type(flat→ivf_vct), 인프라가 **동시에** 바뀌었다. 지연시간 차이를 어느
   한 요인 탓으로 단정하지 말 것.
4. **searchable은 total만.** SDK별 insert→searchable 측정 메커니즘이 다르므로
   단계별 분해 비교는 무의미하고 end-to-end total만 맞댄다.
5. **baseline 기준.** v1.2.2 baseline은 5/15 aligned 측정값을 사용한다(5/12
   production-accumulated 아님).
6. **비교에서 빼야 할 것.** capture의 N ≥ 20,000 ERROR 구간(insert ceiling)과
   §4.4의 두 꼬리 p95는 곡선 fit·비교에서 제외하거나 각주 처리한다.
